## Top Stories

### Zakura 1.3.x Adds the Experimental P2Pv2 Stack

Last week’s issue covered Zakura Common’s cryptographic speedups. The new operator story is Zakura 1.3.x: 1.3.0 was the first node release built on Common, and the official download page now lists 1.3.2, released September 5. The release adds an experimental P2Pv2 consensus engine with verified-header-chain and bounded-DAG validation, alongside peer discovery, RPC visibility, and lightwalletd integration.

The operator detail matters: the experimental engine is disabled by default on mainnet. This is not a consensus change that has activated everywhere; it is a new validation path for operators to evaluate. Mainnet operators should read the release notes and use the current download rather than treating this as a routine wallet update. [Zakura 1.3.0 release notes](https://zakura.com/announcements/zakura-1-3-0/) · [Current downloads](https://zakura.com/download/)

### Vizor Demonstrates a Shielded Ledger Transaction

Vizor published a development-build demonstration of a shielded ZEC transaction signed on a Ledger. The wallet says it intends to be the first wallet supported when the Ledger app goes live, but the demo is not a claim that general Ledger support is already released.

That distinction aside, hardware signing is an important usability milestone: shielded ZEC needs to work with the custody and signing habits people already trust, not only inside software wallets. [Vizor’s demonstration](https://x.com/i/status/2094747602139140393) · [Follow-up on the Ledger app](https://x.com/i/status/2094747604190150868)

### Coinbase-Wrapped ZEC Arrives on Base

cbZEC, a Coinbase-custodied wrapped representation of ZEC, appeared on Base this week and began showing up in Base ecosystem integrations. It creates a new route into Base liquidity and DeFi, but it is not a shielded-pool asset: the token is a transparent wrapped representation backed by ZEC held in custody.

That makes this an access and liquidity story, not a privacy upgrade. Users should understand which side of the bridge they are using and where the privacy boundary ends. [Ecosystem digest](https://x.com/i/status/2096708304328069278) · [cbZEC contract and market data](https://coinmarketcap.com/currencies/coinbase-wrapped-zec/)

## Privacy Corner: The Single-Bit Problem

Maxime Desalle’s *Mastering Zcash* is useful because it treats privacy as a system property, not a magic label attached to a transaction. A shielded transaction can hide its sender, receiver, and amount while the surrounding workflow still reveals a great deal.

The failure can be as small as one bit: a deposit and withdrawal happen within minutes; a merchant knows exactly which customer requested a memo; an exchange sees the same unusual amount enter and leave; or a wallet reuses a public identity around a private payment. One clue can sharply reduce the anonymity set even when the cryptography is working perfectly.

Practical rule: do not treat shielding as the end of the privacy workflow. Avoid immediate, uniquely sized shield/unshield paths when your threat model matters, keep exchange and merchant identities separate from personal addresses, and prefer wallets that make the private path the default. Privacy is not only what the protocol hides; it is also what the surrounding routine makes easy to infer.
